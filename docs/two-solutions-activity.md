# ข้อดีข้อเสีย 2 ทางเลือก — Activity ใน CRM Phase 1

เอกสารตัดสินใจสำหรับคำถามที่ยังเหลืออยู่ข้อเดียว
อ้างอิง ADR-0001 ถึง ADR-0019 · คำถามและคำตอบทั้งหมดดู [interview-log](interview-log.md)

**สิ่งที่ทั้งสองทางเลือกเหมือนกัน (ไม่ต้องถกซ้ำ):**
ทั้งคู่ **ไม่สร้าง Loyalty activity store** ใน Phase 1 — ADR-0002 ยังยืนทั้งสองทาง
เพราะ Fabric เก็บ behavioral event ให้อยู่แล้ว และธุรกิจไม่ต้องการแต้มย้อนหลัง
สิ่งที่ต่างกันคือ **CRM Activity object** ซึ่งเป็นคนละเรื่องกัน

---

# ทางเลือก A — ไม่มี Activity ใน Phase 1 เลย

*(สถานะปัจจุบันของเอกสาร: ADR-0007)*

Phase 1 ส่งมอบเฉพาะ Customer Master และชั้นความสัมพันธ์ ไม่มี Activity object
ทั้งของพนักงานและของ Loyalty เลื่อนทั้งหมดไป phase ถัดไป

## ข้อดี

- **Timeline** — ขอบเขต Phase 1 แคบที่สุด ไม่มีอะไรมาแย่งเส้นทางวิกฤต
- **ตรง mandate** — "Customer Data First" แบบไม่มีข้อโต้แย้งให้ผู้บริหารตั้งคำถาม
- **ไม่ต้องถกเรื่องประเภทกิจกรรม** ซึ่งต้องใช้ input จากทีมหน้างานและยืด requirement phase
- **ไม่เสี่ยงออกแบบผิด** เพราะไม่ได้ออกแบบอะไรเลยบน requirement ที่ยังไม่นิ่ง
- **ไม่มีของที่สร้างแล้วไม่มีคนใช้** — สอดคล้องกับข้อเท็จจริงที่ว่า activity แทบไม่ได้ใช้ใน Phase 1

## ข้อเสีย

- **ถ้า roadmap มี SFA / field sales จะแพงขึ้นมาก** — visit object เป็นแกนที่ order,
  audit และ KPI แขวนอยู่ การเพิ่มทีหลังบนระบบ always-on คือการรื้อ ไม่ใช่การเพิ่ม
  ซึ่งตกในข้อยกเว้นที่ ADR-0016 เขียนกำกับไว้เอง
- **ขัดกับมาตรฐานแพลตฟอร์ม** — CRM ทุกเจ้ามี Activity เป็น standard object ติดมาอยู่แล้ว
  การ "ไม่มี" จึงมักไม่ใช่การประหยัด แต่เป็นการปิดของที่มีอยู่แล้วไม่ให้ใช้
- **กิจกรรมพนักงานช่วง Phase 1 ไม่ถูกเก็บและกู้ไม่ได้** — ไม่มีระบบใดในองค์กร
  เก็บสำรองให้ (ต่างจาก behavioral event ที่ Fabric เก็บ) แม้ปริมาณจะน้อยเพราะ
  แทบไม่ได้ใช้อยู่แล้ว
- **โมดูลที่ต้องใช้ประวัติการติดต่อจะทำงานไม่เต็มรูป** ถ้าถูกดึงเข้า Phase 1 ภายหลัง
- **ยังต้องกลับมาตัดสินใจเรื่องนี้อีกครั้งอยู่ดี** — เลื่อนคำถาม ไม่ได้ตอบคำถาม

# ทางเลือก B — นิยาม Activity object มาตรฐานใน Phase 1 แต่ยังไม่เปิดใช้

*(ข้อเสนอใน ADR-0019)*

สร้าง Activity object ขั้นต่ำตามมาตรฐานแพลตฟอร์ม (ลูกค้า/lead ที่อ้างถึง, ประเภท,
เจ้าของ, เวลา, ช่องทาง, เรื่อง, ผลลัพธ์) ไว้ในโครงสร้างตั้งแต่ Phase 1
ปิดไม่ให้ใช้งานไว้ก่อน แล้วเปิดเมื่อถึง phase ที่มีคนใช้จริง

## ข้อดี

- **ปลดบล็อกทันทีโดยไม่ต้องรอใคร** — CRM Activity ไม่มี business rule ของ Loyalty
  อยู่เลย จึงไม่เคยต้องรอ Loyalty confirm ตั้งแต่แรก การรออยู่ตอนนี้คือรอทีมที่
  ไม่เกี่ยวตอบคำถามคนละข้อ
- **รองรับ SFA ที่เป็นหัวใจของ FMCG** — ถ้า roadmap มี field sales / เยี่ยมร้าน
  โครงสร้างพร้อมแล้ว ไม่ต้องรื้อระบบที่วิ่งอยู่
- **สอดคล้องกับ ADR-0016 ในกรณีที่ Activity เป็น core-structural** — ทำตอนที่ยังไม่มี
  ใครพึ่งพาคือจังหวะที่ถูกและปลอดภัยที่สุด
- **ตรงกับมาตรฐานแพลตฟอร์ม** — ไม่ต้องฝืนปิด object ที่ระบบมีมาให้อยู่แล้ว
- **ปิดประเด็นนี้ได้จบ** ไม่ต้องยกกลับมาถกใหม่ทุก phase

## ข้อเสีย

- **กินเวลา Phase 1 เพิ่ม** แม้จะไม่มาก แต่ timeline คือข้อจำกัดจริงข้อหนึ่ง
- **สร้างของที่ยังไม่มีคนใช้** ซึ่งขัดกับข้อเท็จจริงที่ว่า activity แทบไม่ได้ใช้ใน Phase 1
- **เสี่ยงถูกมองว่าเป็น scope creep** ต่อ mandate "Customer Data First" ถ้าอธิบาย
  ไม่ชัดว่าเป็นโครงสร้าง ไม่ใช่ feature
- **ถ้านิยามผิด ยังต้องแก้อยู่ดี** — ความเสี่ยงลดลงเพราะใช้โครงมาตรฐานที่ไม่ผูก
  business rule แต่ไม่ได้เป็นศูนย์
- **ต้องมีวินัยไม่ให้ของที่ปิดไว้ถูกแอบใช้** — object ที่มีอยู่แต่ไม่มีกติกากำกับ
  มักถูกเอาไปใช้ผิดวัตถุประสงค์ แล้วกลายเป็นหนี้ทางเทคนิคเงียบๆ

---

# ตัวชี้ขาด

**roadmap ของ CRM นี้จะมี field sales / SFA / เยี่ยมร้าน / route-to-market หรือไม่**

| คำตอบ | ทางเลือกที่ควรใช้ | เหตุผล |
|---|---|---|
| **มี** (ปกติของ FMCG) | **B** | Activity เป็น core-structural การเลื่อนทำให้แพงขึ้น ไม่ใช่ถูกลง |
| **ไม่มีเลย** จำกัดแค่ customer master + ชั้นความสัมพันธ์ + lead management | **A** | ไม่มีอะไรมาพึ่ง Activity ปล่อยไว้ก่อนได้จริง |

## คำถามที่ต้องไปถามทีมแพลตฟอร์ม

> "ถ้า Phase 1 ไม่มี Activity object เลย แล้วอีก 6-12 เดือนค่อยเพิ่ม
> จะต้องแก้ของที่มีข้อมูลอยู่แล้วไหม หรือเป็นแค่การเพิ่ม object ใหม่"

ถ้าตอบว่า "ต้องแก้ของเดิม" → **B**
ถ้าตอบว่า "เพิ่มใหม่ได้เลย" หรือ "แล้วแต่จะออกแบบ" → **A** ใช้ได้

# คำแนะนำ

**ทางเลือก B** โดยมีเงื่อนไขว่านิยามเฉพาะโครงขั้นต่ำและปิดไว้ก่อน

เหตุผลหลักไม่ใช่เรื่องเทคนิค แต่เป็นเรื่อง **ต้นทุนของการรอ**: ทางเลือก A
ไม่ได้ตอบคำถาม แต่เลื่อนคำถามออกไป และระหว่างที่เลื่อน ทีมจะยังรอ Loyalty confirm
สิ่งที่ Loyalty ไม่เคยต้องเป็นคนตอบ ส่วนทางเลือก B ปิดเรื่องนี้ได้จบด้วยต้นทุน
ที่เล็กกว่าการยกกลับมาถกใหม่ในทุก phase

ถ้าเลือก B **ADR-0007 ต้องถูกจำกัดขอบเขต** จาก "ไม่มี activity เลยใน Phase 1"
เป็น "มีโครงสร้าง Activity ตั้งแต่ Phase 1 แต่ยังไม่เปิดใช้งาน"
