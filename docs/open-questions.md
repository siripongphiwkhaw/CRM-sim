# Open Questions & Risk Register

เรื่องที่ยังไม่มีข้อสรุป เรียงตามความเสี่ยง — แต่ละข้อระบุว่า **ต้องตัดสินใจก่อนอะไร**
เพื่อไม่ให้เรื่องที่ยังรอได้กลายเป็นตัวบล็อก Phase 1 โดยไม่จำเป็น

---

## 1. ช่วงเวลาที่การถอน consent ยังไปไม่ถึง Fabric ⚠️ ความเสี่ยงทางกฎหมาย

**สถานะ:** ยังตอบไม่ได้ — ทีมรับทราบว่าเป็นประเด็นที่น่ากังวล
**เกี่ยวข้อง:** ADR-0012
**เส้นตายในการตัดสินใจ:** ก่อน **แคมเปญแรกที่ยิงจริง** ไม่ใช่ก่อน CRM Phase 1 go-live

### สถานการณ์ที่จะเกิดขึ้นแน่นอน

ลูกค้าโทรเข้า call center บอกว่าไม่ต้องการรับโปรโมชันอีก พนักงานกดถอน consent
ใน CRM ทันที แต่ Fabric มีรอบ sync วันละครั้งตอนตีสอง เช้าวันนั้นแคมเปญยิงออกไป
ก่อน — **ลูกค้าที่เพิ่งถอน consent เมื่อวานได้รับข้อความ** เป็นเคสที่ร้องเรียนได้ตรงๆ
และพิสูจน์ได้ง่ายจากฝั่งลูกค้า เพราะเขามีทั้งเวลาที่โทรและเวลาที่ได้รับข้อความ

### ข้อเสนอแนะ เรียงตามความคุ้มค่า

**1. ตรวจ consent ตอนจะยิง ไม่ใช่ตอนสร้างกลุ่มเป้าหมาย** ← ทำก่อนข้ออื่น

มาตรการนี้ให้ผลมากที่สุดต่อต้นทุนที่ต่ำที่สุด ปกติแคมเปญจะ build audience ไว้
ล่วงหน้าแล้วยิงตามเวลาที่ตั้ง ถ้าเปลี่ยนเป็นตรวจสถานะ consent อีกครั้ง ณ วินาที
ที่จะส่ง ช่องว่างจะหดจาก "หนึ่งวัน" เหลือ "เท่ากับความสดของข้อมูล ณ ตอนยิง"
โดยไม่ต้องรื้อ integration ทั้งระบบ

**2. ส่งเฉพาะ "การถอน" แบบทันที แยกจากรอบ sync ปกติ**

ไม่ต้องทำ integration ทั้งก้อนให้เป็น real-time ทำเฉพาะ event การถอนให้วิ่ง
ทันทีในรูป suppression list ส่วน consent ที่ให้ใหม่ปล่อยไปตามรอบเดิม เพราะ
**ความเสี่ยงสองทางนี้ไม่สมมาตร**: ถอนช้าคือยิงหาคนที่ไม่ยินยอมซึ่งผิดกฎหมาย
ส่วนให้ช้าคือเสียโอกาสทางการตลาดหนึ่งรอบเท่านั้น การใช้ SLA เดียวกันทั้งสองทาง
แปลว่าจ่ายค่าระบบ real-time ให้ฝั่งที่ไม่ต้องการ หรือไม่ก็ยอมรับความเสี่ยงทาง
กฎหมายในฝั่งที่ต้องการ

**3. เก็บหลักฐานว่า ณ เวลาที่ยิง ระบบเห็นสถานะ consent เป็นอะไร**

ข้อนี้ไม่ได้ลดโอกาสเกิด แต่ลด**ความรับผิด** ถ้าพิสูจน์ได้ว่าระบบตรวจแล้วและ
เห็นว่ายังยินยอมอยู่ตามกระบวนการที่มีเอกสารรองรับ สถานะทางกฎหมายต่างจาก
กรณีที่ไม่มีหลักฐานอะไรเลยโดยสิ้นเชิง เก็บคู่กับ log การยิงแต่ละครั้ง

**4. มาตรการชั่วคราวระหว่างที่ยังไม่มีข้อ 1-2**

ให้ call center มีช่องทางแจ้ง marketing ทันทีเมื่อมีการถอน consent และ
ให้ทีมแคมเปญ build audience ใกล้เวลายิงที่สุดเท่าที่ทำได้ วิธีนี้ไม่ยั่งยืน
แต่ใช้ประคองได้ระหว่างรอของจริง

### สิ่งที่ต้องตัดสินใจ และใครควรเป็นคนตัดสิน

| คำถาม | คนที่ควรตัดสิน |
|---|---|
| ยอมรับ lag ได้กี่ชั่วโมงสำหรับการถอน consent | DPO / ฝ่ายกฎหมาย ไม่ใช่ทีมไอที |
| ถ้า CRM ล่ม Fabric ยิงแคมเปญต่อได้หรือไม่ | DPO ร่วมกับ marketing ops |
| ใครชนะเมื่อ consent สองฝั่งไม่ตรงกัน | สถาปนิกข้อมูล ตามหลักของ ADR-0010 |

**ข้อควรระวัง:** อย่าเลือกกติกา "ค่าที่ใหม่กว่าชนะ" ADR-0010 ระบุไว้เองว่า field
ที่ต้องใช้กติกานี้คือ field ที่ยังไม่มีเจ้าของจริง สำหรับข้อมูลทั่วไปผลคือข้อมูลเพี้ยน
แต่สำหรับ consent ผลคือ **ไม่มีคำตอบเดียวว่าลูกค้ายินยอมหรือไม่** ซึ่งเป็นสิ่งที่
ต้องตอบให้ได้ถ้าถูกตรวจสอบ

## 2. ช่วงรอรหัสลูกค้าจาก SAP หลังปิดดีล

**สถานะ:** เปิดค้าง — เลือก ADR-0009 (b) แล้ว แต่ไม่ได้รับกลไกกันชน (c)
**เส้นตาย:** ก่อน Lead Management ขึ้นใช้งานจริง

หลังปิดดีล ลูกค้ารายนั้นยังไม่มีตัวตนใน CRM จนกว่า SAP จะเปิดรหัส ยังไม่มีคำตอบว่า
ระหว่างนั้น CRM แสดงอะไร ความเสี่ยงคือทีมขายจะสร้างลูกค้าซ้ำเองใน CRM เพื่อเลี่ยง
การรอ ซึ่งย้อนกลับมาทำลาย master control ทางอ้อม

**สิ่งที่ต้องรู้ก่อนตัดสิน:** ที่หน้างานจริง การเปิดรหัสลูกค้าใหม่ใน SAP ใช้เวลานาน
แค่ไหน และใครเป็นคนกด ถ้าเป็นเรื่องของนาที ปล่อยไว้แบบนี้ได้ ถ้าเป็นวันหรือ
ต้องผ่านฝ่ายบัญชี/เครดิต ต้องออกแบบสถานะ prospect รองรับตั้งแต่แรก

## 3. เจ้าของ canonical activity contract

**สถานะ:** ADR-0004 ยังเป็น Proposed
**เส้นตาย:** ก่อนเริ่มงาน integration ฝั่ง Loyalty

ยังไม่มีคำตอบว่าใครในองค์กรเป็นเจ้าของ contract layer นี้ (data architect หรือ
integration team) ถ้าไม่มีเจ้าของ contract จะเน่าและกลายเป็น point-to-point
integration อยู่ดี ซึ่งทำให้เสียค่า re-integration เต็มจำนวนตอน FY2028

## 5. การรวมโปรไฟล์ที่สถานะ consent ไม่ตรงกัน ⚠️ ความเสี่ยงทางกฎหมาย

**สถานะ:** เปิดค้าง — เกิดจาก ADR-0014
**เส้นตาย:** ก่อนเปิดใช้การรวมโปรไฟล์อัตโนมัติ

เมื่อ Fabric รวมสองโปรไฟล์ที่ฝั่งหนึ่งยินยอมและอีกฝั่งถอน consent ยังไม่มีกติกาว่า
ผลลัพธ์คืออะไร ความเสี่ยงคือคนที่ถอน consent แล้วกลับมามีสถานะยินยอมอีกครั้ง
เพราะไปรวมกับโปรไฟล์ที่ยังยินยอมอยู่

**ข้อเสนอแนะ:** ห้ามตัดสินอัตโนมัติในกรณีนี้ ให้ยึด **สถานะที่เข้มงวดกว่าเสมอ**
(ถือว่าถอน) แล้วส่งให้คนตรวจสอบ อย่าใช้กติกา "ค่าที่ใหม่กว่าชนะ" ด้วยเหตุผลเดียว
กับที่ระบุไว้ในข้อ 1

---

## 4. ยังไม่ได้รับตัว RFP

**สถานะ:** ขอแล้ว ยังไม่ได้รับ — ค้นใน Drive แล้วไม่พบ พบเฉพาะไฟล์บันทึกการประชุม
**ผลกระทบ:** ยังยืนยันขอบเขต Phase 1 จากเอกสารจริงไม่ได้ ทุกข้อสรุปเรื่องขอบเขต
ในชุด ADR นี้จึงอ้างอิงจากคำบอกเล่าในการสัมภาษณ์เท่านั้น ควรตรวจทานกับ RFP
อีกครั้งเมื่อได้รับ
