# สรุปข้อดีข้อเสีย — Activity Master ใน CRM Phase 1

สรุปจาก grilling session ทั้งหมด อ้างอิง ADR-0001 ถึง ADR-0015
ของค้างที่ยังไม่ตัดสิน ดู [open-questions.md](open-questions.md)

---

## ข้อสรุปหลัก

- **CRM Phase 1 ไม่สร้าง Activity Master** — Fabric CDP ยังเป็นเจ้าของ B2C
  behavioral event ต่อไปจนถึง FY2028
- **Phase 1 เก็บเฉพาะ Customer Master** ตาม mandate ไม่รวมการบันทึกกิจกรรมพนักงาน
- **CRM เป็น master ของ "ชั้นความสัมพันธ์"** (ผู้ติดต่อ, consent, ประวัติบริการ,
  ความชอบ) ส่วน identity เป็นของ SAP (B2B) และ Fabric (B2C)
- เหตุผลชี้ขาดคือ **ไม่มีข้อมูลใดสูญหาย** เพราะ Fabric เก็บ raw event อยู่แล้ว
  และ **ธุรกิจไม่ต้องการแต้มย้อนหลัง**

---

## ทางที่เลือก: ไม่มี Activity Master ใน CRM Phase 1

### ข้อดี

- **Timeline** — Phase 1 มีขอบเขตเดียว ไม่มีงานแทรกที่ต้องรอ spec จากทีมอื่น
- **Master control** — ไม่เกิด B2C master ซ้อนสองที่ยาว ~2 ปีจนถึง FY2028
  ซึ่งเป็นกรณีที่แย่ที่สุดของการกำกับข้อมูล
- **Budget** — ไม่จ่ายค่าสร้าง store ที่จะถูกรื้อหรือรวมร่างอยู่ดีตอน FY2028
- **Workload** — CRM ไม่ต้องแบกงาน ingest จาก Social / Supermetrics / EC mall
  ซึ่งเป็นงานของ CDP โดยธรรมชาติ
- **Management** — ตอบผู้บริหารได้ตรงกับ mandate "Customer Data First" ไม่มี
  ข้อครหาเรื่อง scope creep
- **ไม่มีภาระทางการเงินแฝง** — ไม่สัญญาแต้มย้อนหลัง จึงไม่มีแต้มค้างจ่าย
  และไม่ต้องทำ reconciliation ระดับการเงินใน Phase 1

### ข้อเสีย / สิ่งที่ต้องยอมรับ

- **พึ่ง Fabric สำหรับ Customer 360** — เกิด dependency ด้าน availability และ
  ความสดของข้อมูล ซึ่งยังไม่มีข้อตกลงกำกับ
- **ข้อมูลช้าหนึ่งวันเสมอ** — batch รายวัน D-1 ทำให้พนักงานเห็นภาพของเมื่อวาน
  ไม่พอสำหรับ consent และไม่พอเมื่อลูกค้าถามถึงรายการที่เพิ่งเกิดเมื่อเช้า
- **กิจกรรมของพนักงานช่วง Phase 1 ไม่ถูกเก็บและกู้ย้อนหลังไม่ได้** — ต่างจาก
  behavioral event ตรงที่ **ไม่มีระบบใดในองค์กรเก็บสำรองไว้เลย** ถ้าไม่เก็บ
  ข้อมูลนั้นจะไม่เคยมีอยู่
- **มีงาน migration รออยู่ที่ FY2028** ตอน activity ย้ายเข้ามาใน CRM
- **โมดูลที่ต้องใช้ประวัติการติดต่อจะทำงานได้ไม่เต็มรูป** ถ้าถูกรวมไว้ใน Phase 1

---

## ทางที่ไม่ได้เลือก: สร้าง Activity Master ใน CRM ตั้งแต่ Phase 1

### ข้อดีที่เสียไป

- มี single source of truth ตั้งแต่วันแรก ไม่ต้อง reconcile ทีหลัง
- Loyalty มาถึงแล้วแค่อ่าน ไม่ต้องสร้าง data model ใหม่
- มีข้อมูลพฤติกรรมสะสมล่วงหน้าก่อน Loyalty เปิด

### ข้อเสียที่หลบได้

- ออกแบบบน requirement ที่ยังไม่ confirm → เสี่ยงต้อง migrate schema + backfill
  ตอนที่ timeline ตึงที่สุด
- รัน B2C master ซ้อนสองที่จนถึง FY2028
- จ่ายค่าออกแบบเกินความจำเป็นของ Phase 1 (points logic, tier, multiplier)
- ทีม CRM ต้องออกแบบ domain ของทีมอื่นโดยไม่มีเจ้าของ requirement มา sign-off

## สรุปตามมิติที่ตั้งคำถามไว้ตอนต้น

| มิติ | ผลของทางที่เลือก |
|---|---|
| **Management** | ตรงกับ mandate, มีของส่งมอบที่อธิบายได้ (ชั้นความสัมพันธ์), ไม่มี scope creep |
| **Data** | ไม่มีข้อมูลสูญหาย เพราะ Fabric เก็บให้อยู่แล้ว — ยกเว้นชั้นกิจกรรมพนักงานที่ยอมเสีย |
| **Workload** | ไม่แบกงาน ingest หลายช่องทาง, ไม่ต้องทำ reconciliation ระดับการเงิน |
| **Budget** | ไม่จ่ายค่า store ที่จะถูกรื้อตอน FY2028 (budget ไม่ใช่ข้อจำกัดจริงของโปรเจกต์นี้) |
| **Timeline** | ปลดงานที่ต้องรอ spec จากทีมอื่นออกจากเส้นทางวิกฤต |

---

## จุดที่ต้องเฝ้าระวังต่อ

- **consent lag** — batch รายวันทำให้การถอน consent ไปถึง Fabric ช้า
  เป็นความเสี่ยงทางกฎหมาย ไม่ใช่แค่เรื่องคุณภาพข้อมูล (register ข้อ 1)
- **การรวมโปรไฟล์ที่ consent ไม่ตรงกัน** — ห้ามตัดสินอัตโนมัติ (register ข้อ 5)
- **ช่วงรอรหัสลูกค้าจาก SAP** — เสี่ยงทีมขายสร้างลูกค้าซ้ำเพื่อเลี่ยงการรอ (register ข้อ 2)
- **ตารางเดียวรวม B2C/B2B** — ต้องบังคับไม่ให้ field ข้ามฝั่งกัน และต้องมี key
  ภายในของ CRM เอง (ADR-0015)
- **ยังไม่ได้ตรวจทานกับ RFP** — ข้อสรุปเรื่องขอบเขตทั้งหมดมาจากการสัมภาษณ์เท่านั้น
