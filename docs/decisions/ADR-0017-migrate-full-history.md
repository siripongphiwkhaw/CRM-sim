# ADR-0017 — Phase 1 migrate ข้อมูลเดิมทั้งหมด รวมประวัติย้อนหลัง

**สถานะ:** Accepted
**เกี่ยวข้อง:** ADR-0011 (CRM เป็นเจ้าของชั้นความสัมพันธ์), ADR-0016 (always-on)

## Context

ADR-0011 และ ADR-0013 ทำให้ขอบเขต migration เล็กลงโดยอัตโนมัติ — identity
ไม่ต้อง migrate เลย เพราะ B2B ไหลมาจาก SAP และ B2C มาจาก batch รายวัน

ทางเลือกที่พิจารณา: (a) ไม่ migrate อะไรเลย · (b) เฉพาะชั้นความสัมพันธ์
(ผู้ติดต่อ, consent เดิม, เคสที่ยังเปิดค้าง) · (c) ทุกอย่างรวมประวัติย้อนหลัง

ข้อเสนอเดิมคือ (b) โดยชี้ว่า consent เดิมเป็นชิ้นที่ห้ามพลาดเพราะสร้างใหม่ไม่ได้
ส่วนประวัติย้อนหลังเป็นงานที่กินเวลามากที่สุดและมีคนใช้จริงน้อยที่สุด

## Decision

เลือก **(c) — migrate ข้อมูลเดิมทั้งหมด รวมประวัติย้อนหลัง**

## Consequences

**สิ่งที่ได้**

- ผู้ใช้เห็นภาพลูกค้าครบตั้งแต่วันแรกที่เปิดระบบ ไม่มีช่วง "ระบบใหม่ว่างเปล่า"
  ซึ่งเป็นสาเหตุที่ทำให้ผู้ใช้ไม่ยอมย้ายมาใช้ระบบใหม่บ่อยที่สุด
- ไม่ต้องเปิดระบบเก่าค้างไว้ให้คนกลับไปดูประวัติ

**ความเสี่ยงที่ต้องบริหาร**

1. **นี่คือความเสี่ยงต่อ timeline อันดับหนึ่งของ Phase 1** ประวัติย้อนหลังมักเป็น
   ข้อมูลที่สกปรกที่สุด (รูปแบบไม่นิ่ง ข้อมูลซ้ำ ข้อมูลขาด เจ้าของไม่ชัด)
   และงาน cleansing ประมาณการต่ำกว่าความจริงเสมอ ต้องกันเวลาไว้เผื่อ
2. **ต้องระวังไม่ให้ขัดกับ ADR-0011** — ถ้า migrate ประวัติของสิ่งที่ CRM ไม่ได้เป็น
   master (เช่น ประวัติธุรกรรมที่เจ้าของคือ Fabric หรือ SAP) จะได้สำเนาที่เก่ากว่า
   ต้นฉบับมาเก็บไว้ ซึ่งเป็นปัญหาเดียวกับที่ ADR-0002 หลบมาตลอด
   **ให้ migrate ประวัติของชั้นความสัมพันธ์เป็นหลัก** ส่วนประวัติของชั้น identity
   ให้ชี้ไปที่ต้นทางแทนการคัดลอก
3. **consent เดิมเป็นชิ้นเดียวที่พลาดไม่ได้** เพราะสร้างใหม่ไม่ได้และมีผลทางกฎหมาย
   ถ้าไม่ได้มา เหลือทางเลือกแค่ไปขอ consent ใหม่ทั้งฐาน (ได้กลับไม่ครบแน่นอน
   เสียฐานการตลาดถาวรส่วนหนึ่ง) หรือยิงแคมเปญโดยพิสูจน์ความยินยอมไม่ได้
   **ต้อง migrate ให้ได้ทั้งสถานะและหลักฐาน** — ใครยินยอม เมื่อไหร่ ช่องทางไหน
   ข้อความเวอร์ชันไหน ถ้าระบบเดิมมีแค่ flag ยินยอม/ไม่ยินยอม จะได้มาแค่สถานะ
   แต่ไม่ได้หลักฐาน ซึ่งเป็นคนละเรื่องกันเมื่อถูกตรวจสอบ

**ข้อเสนอเชิงปฏิบัติ (ตามหลัก ADR-0016)**

การเลือก (c) ไม่ได้บังคับว่าต้องยกทุกอย่างเข้าให้เสร็จ *ก่อน* go-live
บนระบบ always-on การ migrate แบบ big-bang เป็นรูปแบบที่เสี่ยงที่สุด แนะนำให้แบ่ง:

- **ก่อน go-live:** ชั้นความสัมพันธ์ที่ใช้งานจริงทุกวัน + consent เดิมทั้งหมด
- **หลัง go-live (backfill):** ประวัติย้อนหลังส่วนที่เหลือ ทยอยยกเข้าเป็นงาน
  *additive* ซึ่งไม่กระทบผู้ใช้และย้อนกลับได้ถ้ามีปัญหา

วิธีนี้ยังได้ผลลัพธ์ตาม (c) ครบ แต่ย้ายความเสี่ยงส่วนใหญ่ออกจากเส้นทางวิกฤต
ของ Phase 1
