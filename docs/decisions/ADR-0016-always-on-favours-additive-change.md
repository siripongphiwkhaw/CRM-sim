# ADR-0016 — CRM และ Loyalty เป็นระบบ always-on จึงต้องเลือกทางที่การเปลี่ยนแปลงในอนาคตเป็นแบบ "เพิ่มของใหม่" ไม่ใช่ "รื้อของเดิม"

**สถานะ:** Accepted
**เสริมเหตุผลให้:** ADR-0002, ADR-0007

## Context

ข้อมูลเพิ่มเติมจากทีม:

1. **Activity แทบไม่ได้ใช้ใน Phase 1 เลย**
2. **การทำ activity ยังไม่ได้รับการ confirm จาก Loyalty project**
3. **CRM และ Loyalty เป็นระบบ always-on** — จังหวะการ redesign จะกระทบต่อ
   การทำงานในส่วนต่างๆ ของทั้งสองระบบ

ข้อ 3 เปลี่ยนวิธีตั้งคำถาม เดิมเราถามว่า "สร้าง Activity Master ตอนนี้ หรือรอ
Loyalty confirm ก่อน" ซึ่งตั้งอยู่บนสมมติฐานเงียบๆ ว่าอนาคตจะมีช่วงว่างให้แก้
แต่เมื่อทั้งสองระบบเป็น always-on **ไม่มีช่วงว่างนั้นอยู่จริง** — ทุกการเปลี่ยนแปลง
นับจากนี้เกิดขึ้นบนระบบที่มีผู้ใช้และข้อมูลจริงวิ่งอยู่

คำถามที่ถูกต้องจึงเป็น: **การเปลี่ยนแปลงแบบใดที่ทำบนระบบ live แล้วเจ็บน้อยกว่า**

## Decision

ยืนตาม ADR-0002 และ ADR-0007 (ไม่สร้าง Activity Master และไม่บันทึก staff activity
ใน Phase 1) โดยเพิ่มเหตุผลรองรับจากข้อจำกัด always-on:

**เลือกทางที่ทำให้การเปลี่ยนแปลงในอนาคตเป็นการ "เพิ่มโครงสร้างใหม่" (additive)
ไม่ใช่การ "แก้โครงสร้างเดิมที่มีข้อมูลและมีคนใช้อยู่" (migration)**

เหตุผล: บนระบบ always-on การเพิ่มตารางหรือโมดูลใหม่ที่ยังไม่มีใครพึ่งพา เป็นงานที่
ควบคุมความเสี่ยงได้ ปิด feature flag ไว้ก่อนได้ ทยอยเปิดได้ แต่การแก้โครงสร้างที่มี
ข้อมูลจริงและมีระบบอื่นอ่านอยู่แล้ว ต้องทำ migration ซึ่งกระทบผู้ใช้จริงและย้อนกลับยาก

ถ้าสร้าง Activity Master ตอนนี้บน model ที่ Loyalty ยังไม่ confirm แล้ววันหนึ่ง
Loyalty confirm มาไม่ตรงกัน สิ่งที่ต้องทำคือ **migration บนระบบที่วิ่งอยู่ทั้งสองฝั่ง
พร้อมกัน** ซึ่งเป็นกรณีที่แพงและเสี่ยงที่สุดในบรรดาทางเลือกทั้งหมด

## Consequences

- **ความเสี่ยงที่บันทึกไว้ใน ADR-0007 เบาลง** — เดิมบันทึกว่ายอมเสียข้อมูลกิจกรรม
  พนักงานช่วง Phase 1 แบบกู้ไม่ได้ แต่เมื่อ activity แทบไม่ได้ใช้ใน Phase 1 อยู่แล้ว
  ปริมาณสิ่งที่เสียไปจึงน้อยกว่าที่ประเมินไว้ตอนแรกมาก
- **ADR-0004 (canonical activity contract) มีค่ามากขึ้น ไม่ใช่น้อยลง** — บนระบบ
  always-on การมี contract ที่นิยามไว้ล่วงหน้าทำให้ Loyalty เอา activity เข้ามา
  ต่อได้โดยไม่ต้องแตะสิ่งที่วิ่งอยู่ ซึ่งตรงกับหลักการ additive ของ ADR นี้พอดี
  จึงควรผลักดันให้หา**เจ้าของ contract** โดยเร็ว (open-questions ข้อ 3)
- **ทุกการออกแบบนับจากนี้ต้องถามเพิ่มหนึ่งคำถามเสมอ:** ถ้าอนาคตต้องแก้สิ่งนี้
  จะเป็นการเพิ่มของใหม่ หรือต้องรื้อของที่คนใช้อยู่ ถ้าเป็นอย่างหลัง ให้ถือว่า
  ต้นทุนที่แท้จริงสูงกว่าที่ประมาณการไว้เสมอ
- ข้อควรระวัง: หลักนี้ไม่ได้แปลว่า "เลื่อนทุกอย่างออกไปให้หมด" การเลื่อนจะได้ผลก็
  ต่อเมื่อสิ่งที่เลื่อนสามารถเพิ่มเข้ามาภายหลังแบบ additive ได้จริง ถ้าสิ่งใดต้อง
  ฝังลงในโครงสร้างแกนกลางตั้งแต่แรก การเลื่อนจะทำให้แพงขึ้น ไม่ใช่ถูกลง
