# ADR-0015 — เก็บลูกค้า B2C และ B2B ในตารางเดียว แยกด้วย field ประเภท

**สถานะ:** Accepted
**เกี่ยวข้อง:** ADR-0009 (SAP สร้าง B2B), ADR-0010 (เจ้าของราย field), ADR-0013 (batch B2C)

## Context

ลูกค้า B2C และ B2B มาจากคนละ master (Fabric vs SAP) คนละวิธีเกิด
(batch D-1 vs SAP สร้างแล้ว sync) คนละกติกาความเป็นเจ้าของ field และ B2B
ยังมีเรื่องเครดิต ภาษี และนิติบุคคลที่ B2C ไม่มี

ทางเลือกที่พิจารณา: (a) ตารางเดียวมี field ประเภท, (b) แยก entity ตาม master
แล้วมีตัวเชื่อมเมื่อเป็นคนเดียวกัน, (c) แยกกันไปเลยไม่เชื่อม

ข้อเสนอเดิมคือ (b) ด้วยเหตุผลว่าทั้งสองฝั่งต่างกันเชิงโครงสร้าง ไม่ใช่แค่ต่างที่ประเภท

## Decision

เลือก **(a) — ตารางเดียว มี field ระบุว่าเป็น B2C หรือ B2B**

## Consequences

**สิ่งที่ได้**

- โครงสร้างเรียบ ค้นหาลูกค้าข้ามประเภทได้จากที่เดียว ไม่ต้อง union สองแหล่ง
- หน้าจอและสิทธิ์การเข้าถึงใช้ชุดเดียวได้ ไม่ต้องทำสองชุดคู่ขนาน

**สิ่งที่ต้องระวังเป็นพิเศษเพราะเลือกทางนี้**

1. **ต้องมี key ภายในของ CRM เอง** — รหัสลูกค้าจาก SAP กับ profile id จาก Fabric
   เป็นคนละ key space จะใช้ตัวใดตัวหนึ่งเป็น primary key ไม่ได้ ต้องมี id ของ CRM
   แล้วเก็บ key ภายนอกทั้งสองเป็นคอลัมน์อ้างอิงแยก บังคับความไม่ซ้ำแยกกันรายฝั่ง
2. **ต้องกันไม่ให้ field ข้ามฝั่งกัน** — field ที่มีความหมายเฉพาะ B2B (เครดิต ภาษี
   นิติบุคคล) ต้องเติมลงแถว B2C ไม่ได้ และกลับกัน ถ้าไม่บังคับด้วยกติกาในระบบ
   ตารางเดียวจะกลายเป็นที่รวมข้อมูลปนกันภายในไม่กี่เดือน
3. **ตารางความเป็นเจ้าของ field (ADR-0010) ต้องระบุเป็นคู่ (field × ประเภทลูกค้า)**
   ไม่ใช่ราย field อย่างเดียว เพราะ field ชื่อเดียวกันอาจมีเจ้าของต่างกันคนละฝั่ง
4. **มีสองแหล่งเขียนเข้าตารางเดียว** — SAP เขียนแถว B2B, batch จาก Fabric เขียนแถว
   B2C ต้องมีการป้องกันไม่ให้แหล่งหนึ่งไปแตะแถวของอีกฝั่ง โดยเฉพาะในงาน
   migration และงานแก้ข้อมูลรายครั้ง
5. **คนคนเดียวที่เป็นทั้งลูกค้า B2C และผู้ติดต่อฝั่ง B2B จะมีสองแถว** ในตารางเดียวกัน
   ยังต้องมีตัวเชื่อมบอกว่าเป็นคนเดียวกัน และ **ห้ามรวมร่างอัตโนมัติ** เพราะ
   consent ของสองฝั่งอาจต่างกันโดยชอบธรรม (รับโปรโมชันส่วนตัว แต่ไม่รับของธุรกิจ)
   การจับคู่ด้วยเบอร์หรืออีเมลผิดพลาดได้ง่าย เช่น เบอร์ร้านที่เป็นเบอร์เจ้าของ
   หรืออีเมลกลางของบริษัท — ถ้าเชื่อมผิดคือข้อมูลลูกค้าสองคนปนกัน ซึ่งเป็นความผิด
   ตาม PDPA ไม่ใช่แค่ข้อมูลเพี้ยน
